## 1. Голоса: сокращение/выделение из распознанного

Проверенные факты:
- Ноты версии — `List<MidiNote>`: `startTick/endTick/pitch/velocity/cents`; все ноты движка — канал 0 (`midi_notes.cpp:480`, `note_on(0, …)`).
- Правки и заглушения — неразрушающие слои над неизменяемой Version; инфраструктура фильтров уже есть (билд #46, «диапазон нот»): правило применяется к списку нот для «Тонов», к song для ABC и единой точкой в `exportMidi` для ▶/экспорта — тем же путём пойдёт и фильтр голосов.
- «Не добавление голосов, а сокращение/выделение» — задача сводится к правилу отбора ОДНОЙ-ДВУХ нот из уже распознанных в каждый момент времени.

Развилки:

1. **Где считать**: (а) GUI, постобработка `v.notes` (Kotlin) — быстро, без пересборки .so, работает задним числом для всех версий, живёт рядом с muted/питч-фильтром; (б) движок (C++) — «глубже» в пайплайне, но пересборка и не нужно для задачи «сокращение результата». **Рекомендация: GUI.**
- решение: пока что GUI, так как для начала нужно иметь возможность увидеть лёгкий результат (возможно, его будет достаточно), но 
2. **Семантика результатa**: (а) неразрушающий слой (отброшенное скрыто, как muted) — материал версии цел, можно вернуть; (б) кнопка [Сократить] — материализует выбор в новую Version (старые остаются в истории). **Рекомендация: слой (а) как основной, (б) — если А.М. захочет «чистую» версию для дальнейших правок.**
- решение: а) материал
3. **Отображение**: (а) скрыть отброшенное (просто, консистентно с #46); (б) покрасить голоса (видно, что отброшено и куда отнесено; 2–3 цвета темы; правки NoteChart). «Выделение требуемого» из запроса ближе к (б).

Алгоритмы (опции запроса):

- **а) 1 голос, самая громкая нота** (loudest): событийный проход по времени; при перекрытии — нота с максимальной velocity (ничья — длиннее/ниже). ~40 строк; предсказуемо; риск — «рвёт» трели и аккорды.
- **б) 1 голос, мелодический переход** — два подварианта:
  - б1 **skyline** — ведущая нота = верхняя звучащая (классическая эвристика выделения мелодии сверху). ~30 строк; хорошо для вокала с аккомпанементом; на низкой мелодии с верхними обертонами ошибается.
  - б2 **плавность (DP/Viterbi)** — линия, максимизирующая Σ [вес·velocity − штраф·|Δpitch| − штраф·(разрыв во времени)]; буквально «мелодический переход». ~100–150 строк; лучше по смыслу, субъективнее в настройке весов.
- **в) 2 голоса**:
  - в1 **порог по питчу** (А.М. задаёт границу — как диапазон нот в #46): выше границы — верхний голос, ниже — нижний. ~30 строк; наглядно, полностью управляемо.
  - в2 **две линии трекингом** — жадное/динамическое ведение двух линий с запретом пересечений. ~120 строк; работает без границы, но сложнее и капризнее.
- **г) неограничено** = выкл (текущее поведение). По умолчанию — «неограничено».

Экспорт двух голосов (MIDI): развилка — (i) один трек, два канала (0/1) — компактно; (ii) два трека (две партии) — надёжнее для MuseScore; как MuseScore покажет (i) — !ai, нужна проверка. Для одного голоса — как сейчас (канал 0).

Объём: а)+б1)+в1)+г) — один билд (~250 строк Kotlin + селектор в ☰-меню + prefs); б2)/в2) — второй билд.

## 2. Обзор кадрового материала (88 × 11.6 мс)

Проверенные факты:
- Модель даёт три тензора `[кадры × 88]` float: `notes` (вероятность тона), `onsets` (атаки), `contours` (микротон) — `ort_inference.cpp` (unwrap), кадр = 256 сэмплов @ 22050 = **11.61 мс** (86.13 кадр/с), индекс 0 = MIDI 21 (A0), 88 клавиш = 21..108 (совпадает с диапазоном #46).
- 0.5 МБ аудио (16 бит моно 22050) ≈ 11.9 с ≈ **1024 кадра**. Полный ролл: float32 ≈ 360 КБ, uint8 ≈ 90 КБ, max-pool ×4 uint8 ≈ 22 КБ.
- Наружу сейчас отдаётся только сводка `frames_json` (~1 КБ, схема v2m-frame-features-2, фиксированные пороги 0.5); полные тензоры живут только во время прогона и уничтожаются (`libv2m.cpp`, `frame_features.cpp`). В GUI попадает сводка последнего прогона (Выход, `Version.framesJson`).
- velocity ноты = средняя вероятность по кадрам × 127; «компрессор» — `v' = 127·(v/127)^(1/(1+2·velocityCompress))` (поднимает тихие ноты). Амплитуда до компрессора наружу не выходит.
- «Вход» и «Выход» — два прогона одного PCM: инференс детерминирован, тензоры одинаковы, отличается только пост-обработка → **ролл один на версию** (дважды считать не нужно).

Варианты:

- **A (рекомендуется, ~1 билд)**: новый C-API (например, `v2m_transcribe_roll`) возвращает прореженный ролл uint8 с max-pool ×4 (≈22 КБ) + ноты с амплитудой до компрессора; JNI → `Version.roll`. GUI: секция/вкладка «Материал» — облако «время × питч» (яркость = вероятность, прорежённый ролл), слой атак (та же «ритмика») и сетка тактов; тап/клик — базовая гистограмма громкостей/уверенностей, отпускание — после обработок (компрессор). Рендер — ImageBitmap (CPU → картинка), быстрее Canvas-прямоугольников на 88×1024.
- **B (~2–3 билда)**: полный float-ролл, зум/скролл по времени, линии порогов onset/frame, сравнение роллов «Вход/Выход».
- **C**: ролл выгружается файлом (`.roll.bin`/JSON) при экспорте — для внешнего анализа (numpy/скрипты); UI-обзор — отдельно.

Развилки внутри A: точность (uint8 pool ×2/×4/×8), хранение (в памяти Version ≈90 КБ; 10 версий ≈0.9 МБ — приемлемо, либо файл-кэш ~/.v2m), место в UI (вкладка «Материал» в «Звучании» / отдельная секция), и главный вопрос: **что понимать под «обработками»** — в текущем наборе громкость меняет только `velocityCompress`; пороги/слияние меняют состав нот (это уже «Вход против Выхода», а не «базовая против обработанной»).

Тап/удержание: в коде уже есть рабочий паттерн — pointerInput с Initial-пассом (строка ABC), нажатие → базовая, отпускание → обработанная.

## Дополнение (2026-09-11, вопросы А.М.): размеры ролла и домены обработок

### Д1. Что означают «float32 ≈ 360 КБ / uint8 ≈ 90 КБ / max-pool ×4 ≈ 22 КБ»

Расчёт для примера «0.5 МБ аудио»: 16 бит моно 22050 = 44100 Б/с → 0.5 МБ ≈ 11.9 с; кадр = 256 сэмплов = **11.61 мс** (86.13 кадр/с) → ≈ 1024 кадра. Ролл = кадры × 88 (A0..C8 = MIDI 21..108).

Размеры — **на один тензор** (notes или onsets; contours втрое шире — 264 столбца):

| Представление | 12 с (1024 кадра) | 1 с | 60 с (лимит записи) |
|---|---|---|---|
| float32 (4 Б) | 352 КиБ (360 КБ) | 30 КБ | 1.73 МиБ |
| uint8 (1 Б) | 88 КиБ (90 КБ) | 7.6 КБ | 444 КиБ |
| uint8 + max-pool ×4 | 22 КиБ | 1.9 КБ | 111 КиБ |

Что делает каждое сжатие:
- **float32 → uint8**: квантование вероятности шагом 1/255 ≈ 0.4 % — для облака и гистограмм незаметно.
- **max-pool ×4**: 4 соседних кадра (46.4 мс) сворачиваются в один по максимуму — пики/атаки сохраняются, но время грубеет до 46 мс, «уверенность» становится максимумом за окно (не средней).
- Оба вместе — 16× от float32. Для облака нужны **notes + onsets** (45 КБ/версия при pool ×4 uint8); contours — только микротон, не обязателен. 10 версий в памяти ≈ 0.45 МБ.

Оговорка о рендере: pool ×4 даёт 256 столбцов на 12 с (21.5 столбца/с) — при канвасе ~1000 точек колонка ≈ 4 px; если детальность важнее, брать pool ×2 (512 столбцов, 45 КБ/тензор) и сводить к пикселям на рендере.

### Д2. Где работает «компрессор» и куда встают gate/low-hi-cut/expander

**Компрессор — не аудио-эффект.** Он не трогает сигнал: это кривая velocity на последнем шаге, уже после распознавания нот — `midi_notes.cpp:467-477` (`velocity = amplitude×127`, затем `v' = 127·(v/127)^(1/(1+2·vc))`), внутри `note_events_to_midi` при записи MIDI-событий. В GUI — ползунок «Компрессия громкости» (`Strings.kt:96`, `App.kt:867`); билд #50 ползунок из GUI убрал (решение А.М.), параметр остался в движке/пресетах/CLI (`--velocity-compress`) — вывод раздела не меняется; в `neutralMelody` не нейтрализуется → действует в обоих прогонах («Вход» и «Выход»).

Пайплайн (`libv2m.cpp:129-172`):

```mermaid
flowchart LR
    A["PCM → ресемпл 22050 (float)"] --> B["ort_inference: тензоры notes/onsets/contours"]
    B --> C["вывод нот: пороги onset/frame, мин. длина, тремоло, melodia-trick"]
    C --> D["гармонизация: слияние, бенды, сдвиг, лад"]
    D --> E["ритм: темп/квант (+ audio_flux по аудио, L688)"]
    E --> F["velocity + компрессор (v' = 127·(v/127)^(1/k))"]
    F --> G["сериализация MIDI"]
```

**Gate / low-hi-cut / Expander — аудио-домен**: их место между ресемплом и моделью (L129 → L130), а не рядом с компрессором. Следствия:
1. меняется вход модели → меняются все тензоры, состав нот, амплитуды; спектральный поток (`audio_flux_oss`) тоже изменится → может измениться автотемп;
2. действуют сразу на обе вкладки («Вход» и «Выход» идут по одному сигналу);
3. «базовое» облако (до обработок) = ролл по сырью. Двухпрогонная схема уже есть: если «Вход» считать по сырому аудио, а «Выход» — по обработанному, базовый и обработанный роллы появятся без третьего прогона модели (сейчас оба прогона по одному и тому же сигналу);
4. применять эффекты в пайплайне (не при захвате) — тогда WAV остаётся сырым, а обработка воспроизводима параметрами.

### Д3. Спектрограмма (первая проба): FFT-библиотека и параметры

**FFT: берём уже имеющееся.** В проекте вендорен Eigen 3.4.90 (`basicpitch/src/basicpitch.cpp/vendor/eigen`, MPL2), и его модуль `unsupported/Eigen/FFT` содержит полную реализацию kissfft внутри (`src/FFT/ei_kissfft_impl.h`). Путь `${BP}/vendor/eigen` уже в include у CLI и libv2m → `#include <unsupported/Eigen/FFT>` работает **без новых зависимостей и без правок CMake**. Бэкенды: kissfft (по умолчанию), pocketfft (нужен внешний `pocketfft_hdronly.h`), FFTW/MKL (внешние библиотеки).

| Вариант | Лицензия | Цена | Комментарий |
|---|---|---|---|
| Eigen::FFT (kissfft внутри) | MPL2 | 0 новых файлов | всё уже в проекте; модуль «unsupported» (API не гарантирован, но версия зафиксирована) |
| KISS FFT отдельно | BSD-3-Clause | ~4 файла | нужен, только если считать в C-коде вне C++ (например, утилита в `tools/`) |
| LSP-DSP-Units | copyleft (Debian: GPL; openSUSE: LGPL-3.0-or-later; точный SPDX — !ai) | DSP-фреймворк | для одного STFT избыточен; интересен только как готовый набор эффектов (gate/expander/EQ) — это отдельное решение |
| FFTW | GPL-2+ или коммерческая | внешняя | лицензионный риск, не нужен |

Примечание: модель получает сырую волну (`ort_inference.cpp:111-117`, input `{chunks, chunk_size, 1}`) — своя спектрограмма считается внутри ONNX-графа и наружу не отдаётся (!ai по составу: гармоническое суммирование). Наш STFT — «обзор сигнала» для пользователя, не «вход модели 1:1».

**Параметры пробы.**
- hop = 256 (11.61 мс) — совпадает с кадрами модели: колонки ложатся в ту же сетку.
- окно: 256 (пример А.М.) → Δf = 86 Гц (грубо); 1024 → 21.5 Гц; 2048 → 10.8 Гц (это и есть практическая нижняя граница «от 10 Гц»). Окно Ханна, перекрытие 87.5 % (2048/256).
- полутоновая детализация на низах физически недоступна: полутон на 100 Гц ≈ 5.9 Гц < Δf(2048) → низы размыты; практичный компромисс — лог-полосы 1/6…1/12 октавы (низы шире).
- ось частот — логарифмическая (10 Гц–10 кГц ≈ 10 октав; линейная ось сожмёт низ). Полосы: ~120 (1/12 октавы), либо 264 (3 на полутон в диапазоне фортепиано A0..C8 — вертикаль совпадёт с роллом модели; на 10 Гц–10 кГц было бы ~360).
- яркость: магнитуда в дБ, пол −80 дБ, нормализация общая (не по кадру — иначе исчезает динамика).
- объём: кадры × полос uint8: 12 с × 120 = 123 КБ (пул ×4 → 31 КБ); 60 с → 620 КБ (пул ×4 → 155 КБ). Стоимость: 1024–5168 БПФ размера 1024/2048 — единицы…десятки мс.

**Проба (предложение).** Как с `tools/rec`: шаг без GUI — флаг CLI (`basicpitch <wav> <out> --spectrogram`) на базе уже читаемого WAV → дамп `.pgm` (P5; без зависимостей, открывается GIMP/просмотрщиком). Смотреть на реальных записях, подобрать окно/дБ/полосы; затем перенос в GUI (вкладка «Материал»). Код STFT — в libv2m (рядом с будущими аудио-эффектами: gate/expander тоже нужны огибающая/спектр), доступ из CLI — через `v2m.h`.

### Д4. Многопроходный анализ и выравнивание громкостей (А.М., 2026-09-12)

Идея А.М.: несколько проходов разными окнами — коротким снять верхние гармоники и вычесть их из файла, средним — основные тоны и вычесть, длинным — басы; плюс выравнивание громкостей (ВЧ слабее СЧ); полосы — логарифмические по сырому WAV.

Оценка:
- **Интуиция верна, реализация проще**: разрешение Δf ≈ 1/T, поэтому ВЧ достаточно короткого окна, НЧ нужно длинное — это постоянная добротность (CQT/вейвлет). Достаточно считать 2–3 STFT (например, окна 256/1024/4096 при общем hop 256) и брать каждую лог-полосу из того прохода, где она разрешена: синтез не нужен, артефактов нет, стоимость ×2–3 (по-прежнему мс). Шов на границах полос — кроссфейд в октаву.
- **Вычитание — дороже и рискованнее**: корректно вычитать только в комплексной области с фазой → анализ-синтез (ISTFT, overlap-add); магнитудное вычитание даёт «музыкальный шум», три round-trip'а накапливают ошибку; для *отображения* выигрыша нет — НЧ ограничены длиной окна, а не маскировкой гармоник; +300–500 строк кода и трудная проверка. Разделение сигнала (гармоники/шум/остаток) — отдельная задача (sinusoidal modeling), не визуализация.
- **Лёгкая замена вычитанию**: наложить на спектрограмму ноты, найденные моделью (ролл, 88 клавиш) — «что в сигнале vs что услышала модель» видно без всякого вычитания.
- **Громкости (п.1.1) — да, стандартно**: спектр гармонических источников спадает ≈ −6 дБ/окт (!ai, правило большого пальца), поэтому в отображении применяют наклон +3…+6 дБ/окт или кривые равной громкости ISO 226 (грубое приближение — A-weighting). Предложение: переключатель наклона 0/+3/+6 дБ на октаву, ISO 226 — позже, если нужен режим «как слышит человек». Это вес *отображения*: на аудио и модель не влияет.
- **Полосы** — логарифмические по сырому WAV (не 88 клавиш); 88 клавиш — только как наложение ролла модели для сравнения.

Порядок пробы: один проход (окно 1024/2048) + наклон + лог-полосы → `.pgm`; затем multi-resolution (2–3 окна с выбором по полосам, ~50 строк) — если картинка зайдёт.
