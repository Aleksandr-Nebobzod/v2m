наша цель -- получать пару подобных  файлов на каждом прогоне (wav->model->quantify+harmonize->manual edit) с тем, чтобы модель могла "втягивать" в себя поправки -- как распознавать вокал конкретного пользователя (с его манерой пения и ошибками) чтобы результат миди был максимально близок к замыслу (не к факту исполнения, а к тем нотам, которые хотел озвучить пользователь), избавляя от manual edit шага всё больше и больше с каждой итерацией "дообучения"
вопрос -- чем надо обогатить выходные файлы, чтобы модель дообучалась эффективнее?

Для эффективного дообучения модели под конкретного пользователя нужно сохранять не только результат, но и **данные для сравнения**: что модель насчитала, как пользователь поправил, и что в итоге должно быть правильным.

### 📦 Что должно быть в выходных файлах для дообучения

Стандартный подход в Basic Pitch — использовать пары `(аудио, MIDI-аннотация)` для обучения . Чтобы модель "втягивала" поправки, нужны три компонента:

| Компонент | Что содержит | Зачем |
| :--- | :--- | :--- |
| **Аудио (WAV)** | Исходная запись пользователя | Вход модели |
| **MIDI-аннотация (GT)** | Итоговые ноты после правок пользователя | Целевой ответ (ground truth) для обучения |
| **JSON-метаданные (опционально)** | Параметры пользователя, уверенность модели, статистика правок | Для взвешенного обучения и анализа |

Это соответствует тому, как Basic Pitch использует датасеты вроде MAESTRO и GuitarSet: аудио в WAV и аннотации в MIDI .

### 🔧 Что добавить в JSON для эффективного дообучения

Твой текущий JSON содержит статистику `notes`, `onsets`, `contours` и `meta`. Для дообучения эффективнее добавить:

1.  **Маски правок пользователя** (`user_corrections`):  
    - Какие ноты были удалены пользователем (ложные срабатывания модели).  
    - Какие ноты были добавлены (пропуски модели).  
    - Какие ноты были сдвинуты по времени/высоте.  
    Это позволяет модели учиться на своих ошибках.

2.  **Параметры уверенности модели** (`confidence_by_note`):  
    Массив с `conf` для каждой ноты в MIDI. Это позволяет при обучении давать больший вес правкам там, где модель была неуверена (например, `conf < 0.5`), и меньший — там, где была уверена и не ошиблась.

3.  **Идентификатор пользователя и версию модели** в `meta`:  
    Чтобы отслеживать прогресс дообучения и разделять данные разных пользователей.

Пример дополнения в JSON:
```json
"user_corrections": {
  "deleted_notes": [{"start_sec": 2.3, "end_sec": 2.7, "pitch": 53}],
  "added_notes": [{"start_sec": 1.8, "end_sec": 2.2, "pitch": 55}],
  "moved_notes": [{"old_pitch": 56, "new_pitch": 57, "time_shift": 0.1}]
},
"confidence_by_note": [0.42, 0.78, 0.91, 0.33],
"meta": {
  "user_id": "user_001",
  "model_version": "v2.3"
}
```

### 🧠 Как использовать эти данные для дообучения

Процесс дообучения можно реализовать так:

1.  **Собирать датасет правок**: После каждой сессии сохранять пары `(аудио, исправленный MIDI, JSON с правками)`.
2.  **Формировать обучающие примеры**: Использовать TFRecord-формат, как в Basic Pitch , где аудио — вход, а ноты/онсеты/контуры из исправленного MIDI — выход.
3.  **Взвешенное обучение**: Использовать уверенность модели из JSON как вес для функции потерь (weighted binary crossentropy). Это стандартный приём в Basic Pitch для борьбы с дисбалансом классов .
4.  **Аугментация**: Применять `pitch shifting` и добавление шума к аудио, чтобы модель не переобучалась под конкретную запись и обобщала манеру пения .

# Глава 2 — Разбор 4-й ссылки (DeepWiki 3.2, TensorFlow Data Pipeline): чем улучшить подход

Разбор выполнил Дис (2026-09-08) по запросу А.М.: «посмотри, чем можно улучшить наш подход». Источник — https://deepwiki.com/spotify/basic-pitch/3.2-tensorflow-data-pipeline#1 (контент получен и сверен с локальным кодом `basicpitch/src/basicpitch.cpp/vendor/basic-pitch/basic_pitch/data/*.py`).

## Устройство пайплайна обучения Basic Pitch

- Обучение идёт **в кадровом пространстве, а не по нотам-событиям**: обучающая пара — `audio_wav` + три разрежённые кадровые матрицы-аннотации: `notes` (нота активна в кадре, 88 бинов), `onsets` (кадр начала ноты), `contours` (питч-контур, суб-полутонное разрешение). MIDI-аннотации конвертируются в эти матрицы заранее (Apache Beam), хранятся разрежённо (indices + values) — пары компактны.
- Во время обучения: запись режется на окна фиксированной длины, разрежённые метки разворачиваются в плотные матрицы, добавляются sample-weights по доступности аннотаций и взвешенная выборка датасетов.
- «Маски правок» (как предлагалось в главе 1) — по сути и есть целевые матрицы: обучающий сигнал — расхождение предсказания модели с аннотацией.

## Чем улучшить наш подход (поправки к главе 1)

1. **Обогащать нужно не JSON-сводку, а пару «до/после» в кадровом представлении.** Полезная единица — «MIDI-правка → кадровые метки notes/onsets (fps движка)». У нас есть обратный конвертер (кадры → MIDI, midi_notes.cpp), прямого нет. Замысел в кадровом виде автоматически «ровный»: нота-правка даёт активные кадры и один onset — без вибрато и дрейфа исполнения. Контур (третий канал BP) для «замысла» почти всегда ровен — учить достаточно notes + onsets.
2. **«Сырьё теряется» (решение Р11) — пересмотреть для Р12.** Выходные тензоры модели (88×T: notes/onsets/contours), которые сейчас выбрасываются после расчёта сводки, — готовый вход для лёгкого обучения без пересчёта CQT (адаптер «вероятности → замысел»). Хранение разрежённое (indices + uint8) — почти бесплатно. Сводка (.frames.json) остаётся человекочитаемым артефактом, тензоры — обучаемым.
3. **Два уровня «втягивания» поправок:**
   - **Уровень A — персонализация пост-обработки (без TensorFlow, реалистично на одном пользователе):** по парам «результат до правок → правка» считать дельты (инструменты уже есть: score_vs_etalon.py, анализаторы mid) и калибровать ручки пост-обработки (слияние фрагментов, снап к ступеням, глобальный сдвиг, пороги, темп) под манеру пользователя. Модель не трогается. Если правки систематичны (детюн, вибрато-дробление, характер атак) — сокращает manual edit сразу.
   - **Уровень B — тонкая настройка сети:** TensorFlow-дообучение на парах (CQT → кадровые GT из правок) по образцу BP: окна, заморозка почти всех весов, малый LR, валидация на прогонах, не участвовавших в обучении. Экспорт в ONNX → подмена весов в C++ (конвейер scripts → model.ort.c уже есть). Только после накопления десятков пар.
4. **Метаданные пары:** user_id (в проекте — author, уже есть в meta), версия весов модели, прогон-id (uuid), связка «до-правок .mid ↔ после-правок .mid ↔ .frames.json ↔ параметры прогона» (параметры уже пишутся в meta-трек .mid). Без прогон-id пара не собирается в датасет.
5. **Формат проще, чем у BP:** TFRecord/Beam не нужны (объёмы — десятки записей): каталог прогона с файлами.

## Предостережения

- «Замысел» не полностью выводим из звука: обучаемо то, что систематично и акустически выражено — манера и ошибки пользователя (детюн, вибрато, дыхание, диапазон, ритмическая неровность). Единичные музыкальные решения («сыграть иначе, чем спето») из звука не выводимы — их доля и есть нижняя граница manual edit.
- Один пользователь = мало данных: только fine-tune с заморозкой или адаптер; валидация обязательна на отложенных прогонах, иначе оценка льстит.
